# 项目可行性报告

## 1. 项目背景与目标

### 1.1 背景

政企、教育、医疗等行业存在大量内网/专网环境，无法使用公网视频会议（腾讯会议、Zoom 等）。这类环境需要一套可私有化部署、数据不出网、适配国产软硬件的视频会议系统。

### 1.2 目标

构建一套基于浏览器的视频会议系统，满足：

- 纯 Web 浏览器访问，无需安装客户端（PWA 可选安装）
- 支持内网私有化部署，数据本地存储
- 适配国产操作系统（麒麟、UOS）与 CPU 架构（x86_64 / aarch64）
- 中小规模会议（≤ 50 人稳定，50-300 人可用）
- 功能对标主流会议产品的核心能力

## 2. 需求分析

### 2.1 核心用户场景

| 场景 | 参与规模 | 关键诉求 |
|------|---------|---------|
| 日常沟通会 | 5-20 人 | 快速开会、音视频、屏幕共享 |
| 部门例会 | 20-50 人 | 预约、主持人管控、聊天 |
| 培训宣讲 | 50-300 人 | 演讲者布局、有序互动 |
| 临时讨论 | 2-5 人 | 极速入会、无需预约 |

### 2.2 功能需求

- 会议生命周期：创建、预约、加入、结束
- 音视频：麦克风/摄像头开关、设备切换、说话指示、静音同步
- 布局：宫格 / 演讲者、头像模式（摄像头关闭时）
- 共享：屏幕共享（整屏/窗口/标签页）
- 互动：举手、实时聊天、弹幕
- 管控：等候室、全体静音、移出成员、结束会议
- 管理：用户管理、会议录制、双语界面

### 2.3 非功能需求

- **部署**：支持离线内网部署，支持国产 OS
- **安全**：HTTPS、密码哈希、令牌鉴权、数据本地化
- **可用性**：服务可 systemd 托管或容器编排
- **兼容性**：Chrome / Edge / Firefox 主流浏览器

## 3. 技术可行性

### 3.1 技术方案选型

#### 实时音视频架构：SFU

经过 P2P / MCU / SFU 三种架构对比，选择 **SFU（Selective Forwarding Unit）**：

| 架构 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| P2P | 无服务器开销 | 端数 × 端数连接爆炸 | ≤ 4 人 |
| MCU | 客户端只需一路流 | 服务器转码 CPU 极高 | 大型研讨 |
| **SFU** | 服务器仅转发不转码，扩展性好 | 每路流独立带宽 | **通用最优** |

#### SFU 实现：mediasoup

对比主流 SFU 实现：

| 项目 | 语言 | 浏览器支持 | 内网部署 | 国产架构 | 结论 |
|------|------|-----------|---------|---------|------|
| **mediasoup 3.14** | C++/Node | ✅ | ✅ | x64/arm64 可编译 | **采用** |
| LiveKit | Go | ✅ | ✅ | 多依赖 | 备选 |
| Janus | C | ✅ | ✅ | 编译复杂 | 备选 |

mediasoup 采用 Node.js 控制面 + C++ Worker，通过 `tsx` 编译 TypeScript，arm64 上需现场编译 Worker（已提供 Dockerfile 与离线打包流程）。

#### 前端：React + Vite + PWA

- React 19 + TypeScript 提供组件化开发与类型安全
- Vite 提供快速 HMR 与构建
- PWA（vite-plugin-pwa）支持离线缓存与可安装
- Ant Design 6 + @ant-design/icons 提供成熟 UI 组件与图标

#### 后端：Fastify + ws

- Fastify 5 提供 REST API（账号、会议、用户管理），性能优于 Express
- `ws` 原生 WebSocket 承载信令，无多余抽象
- TypeScript 全栈类型安全，共享 Zod schema 协议

#### 数据库：MySQL 8 / PostgreSQL 12 可切换

- 通过 `DB_DRIVER` 环境变量切换，`@meeting/db` 适配层屏蔽差异
- 政企既有 MySQL 8（主流），信创环境多配达梦/PG，PG 适配更易扩展
- 迁移脚本按方言分目录（`sql/mysql`、`sql/postgres`）

#### 会话与缓存：Redis 7

- 登录会话存储（7 天 TTL）
- 不作为持久层，停机可重建

### 3.2 关键技术验证

| 技术点 | 验证结论 |
|--------|---------|
| WebRTC 浏览器兼容 | Chrome/Edge/Firefox 均支持，`getUserMedia` / `getDisplayMedia` / `RTCPeerConnection` 均可用 |
| mediasoup 国产 OS 编译 | 麒麟 V10 / UOS 基于 Debian，gcc 工具链可用，arm64 可现场 `npm rebuild` |
| 离线打包 | 同架构编译后 `npm install --omit=dev` + tar 打包，目标机解压安装可行 |
| CRLF 问题 | Shell 脚本在 Linux 因 CRLF 报 `pipefail` 错误，已通过 `.gitattributes` 强制 LF 解决 |
| 说话检测 | Web Audio API `AnalyserNode.getByteTimeDomainData` 计算 RMS，可在前端实时检测 |
| 屏幕共享回环 | 监听 `displaySurface`，全屏/窗口共享时用占位图替代本地预览，消除无限嵌套 |

### 3.3 性能与规模评估

| 规模 | 评估 |
|------|------|
| ≤ 50 人 | 稳定，SFU 转发带宽与 CPU 充裕 |
| 50-300 人 | 可用，建议限制视频路数（仅演讲者出视频），带宽规划 |
| > 300 人 | 超出 MVP 目标，需引入级联或录制直播方案 |

带宽估算（VP8，每路 1Mbps）：N 人全视频会议总带宽 ≈ N × N × 1Mbps。50 人全视频需约 50Mbps 上行（服务器侧），实际建议关闭非发言者视频以降低负载。

## 4. 经济可行性

### 4.1 成本构成

| 项 | 自研私有化 | 公有云会议 |
|----|-----------|-----------|
| 软件许可 | 0（开源技术栈） | 按人/月订阅 |
| 服务器 | 一台即可（8C16G 起） | 云厂商承担 |
| 运维 | 自有运维 | 云厂商承担 |
| 数据安全 | 数据不出网 | 数据上云 |

### 4.2 结论

对中大型政企客户，一次性私有化部署的 TCO 显著低于长期订阅公有云，且满足合规要求。技术栈全部开源，无商业授权风险。

## 5. 法律与合规可行性

- 全部采用开源协议（MIT / ISC / Apache / BSD），无 GPL 传染性风险
- 数据本地存储，满足《数据安全法》《个人信息保护法》对数据不出境的要求
- 适配信创要求：麒麟 / UOS / x86 / arm64

## 6. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| mediasoup arm64 编译失败 | 中 | 提供同架构离线包，避免目标机编译 |
| 浏览器 WebRTC 差异 | 低 | 限定 Chrome/Edge，主流 API 已稳定 |
| 大规模会议带宽不足 | 中 | 限制并发视频路数，演讲者布局 |
| 内网 HTTPS 证书 | 低 | 提供自签证书生成脚本，或接入已有 CA |
| 国产 OS 依赖缺失 | 中 | install.sh 校验 Node ≥ 20，提供依赖说明 |

## 7. 结论

本项目技术可行、经济合理、合规达标。推荐采用 **mediasoup SFU + 自研信令 + MySQL8/PG12 + Redis + Docker/离线包** 的技术组合，分阶段交付：

- **P0（已实现）**：核心会议、音视频、屏幕共享、聊天、管控、用户管理、HTTPS 部署
- **P1**：录制回放完善、大型研讨优化、企业安全增强
- **P2+**：AI 能力、电话互通、跨企业互联
