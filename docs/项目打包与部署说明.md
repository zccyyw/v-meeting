## 〇、构建产物与获取方式

> 📦 安装包统一由 **GitHub Actions** 构建：推送 `v*` tag 后自动并行构建 x64 与 arm64（各使用同架构原生 runner），约 30 分钟产出全部 5 种产物，**无需本地构建环境**。

### 0.1 产物清单

| # | 产物 | Artifact 名称 | 安装介质 | 适用场景 |
|---|------|--------------|---------|---------|
| 1 | 源码包 | `meeting-pack-<ver>-<rel>` | `dist/` 编译产物 | 归档、手动部署 |
| 2 | Docker 镜像包 ⭐ | `meeting-docker-{x64,arm64}-<ver>-<rel>` | 镜像 tar + compose | **有 Docker 的目标机（推荐）** |
| 3 | 离线发布包 | `meeting-native-{x64,arm64}-<ver>-<rel>` | `.tar.gz` + `install.sh` | 无 Docker 的内网 Linux |
| 4 | RPM 包 | `meeting-rpm-{x64,arm64}-<ver>-<rel>` | `meeting-<ver>-<rel>.{x86_64,aarch64}.rpm` | 银河麒麟、中科方德、openEuler 等 RPM 系 |
| 5 | DEB 包 | `meeting-deb-{x64,arm64}-<ver>-<rel>` | `meeting-<ver>-<rel>.deb` | 统信 UOS、方德 DEB 系、Debian/Ubuntu |

> **架构映射**：`x64` → x86_64（海光/兆芯）；`arm64` → aarch64（鲲鹏/飞腾）。**安装包架构必须与目标机 CPU 一致**，跨架构不能安装。

### 0.2 触发构建

```bash
# 方式一：推送 tag（推荐，自动构建两种架构的全部产物）
git tag v0.0.8 && git push origin v0.0.8

# 方式二：GitHub 网页手动触发
#   Actions → Build Packages → Run workflow
#     build_type  : all | pack | docker | native | rpm | deb
#     target_arch : x64 | arm64
#     version     : 0.0.8        release : 1
```

构建完成后在 **Actions → 运行详情 → Artifacts** 下载对应压缩包。

### 0.3 版本约定

tag `v0.0.8` → 包版本 `0.0.8-1`（version-release）。升级时递增版本号或 release，包管理器据此判断新旧并保留配置。

> 💡 各部署方式的**首次安装**与**升级**步骤见 [十一、首次安装与升级](#十一首次安装与升级)；也可直接使用 `docs/install/` 下按方式拆分的独立部署文档（同时提供 docx）。

## 一、概述与部署方式选型

| 方式 | 适用场景 | 优点 | 限制 |
|------|---------|------|------|
| **Docker Compose** | 有 Docker 环境的服务器（x86_64 / arm64） | 一条命令拉起全部服务，含数据库/Redis | 目标机需安装 Docker |
| **离线发布包** | 内网无外网环境、国产 OS（麒麟/UOS） | 目标机无需 npm 网络，systemd 托管 | 需同架构 Linux 构建机打包；需预装 Node.js；依赖 .sh 脚本 |
| **RPM 包** ⭐ | 中科方德等无法执行 .sh 的国产 OS | 内嵌 Node.js，零外部依赖（默认 SQLite+内存 Redis）；systemd 自动迁移；不依赖 .sh | 需 Docker 构建机；仅支持 RPM 系 OS |
| 本地源码运行 | 开发调试 | 灵活，热更新 | 不用于生产 |

> 💡 **选型建议（推荐顺序）**：
> 1. **Docker（镜像包 / Compose）** — 首选。容器内自带运行时与 glibc，与目标机系统版本解耦，国产系统（含麒麟 V10 SP1）可直接运行，升级最快。
> 2. **RPM / DEB 包** — 目标机不允许容器时的首选；内嵌 Node.js，零外部依赖，支持企业级包管理与 `rpm -Uvh` / `dpkg -i` 升级。RPM 系（麒麟/方德/openEuler）用 RPM，DEB 系（UOS/方德桌面/Debian）用 DEB。
> 3. **离线发布包（tar.gz）** — 无 Docker 且无包管理要求的通用 Linux 场景，需目标机预装 Node.js 20+。
> 4. **本地源码运行** — 仅开发调试。

## 二、环境要求与服务端口

### 2.1 目标机通用要求

| 组件 | 要求 | 说明 |
|------|------|------|
| OS | Linux（含麒麟 V10 / UOS / 中科方德）或 Windows Server | 离线包仅支持 Linux |
| CPU | x86_64 或 aarch64 | 与安装包架构一致 |
| Node.js | 20+ | 离线包方式需要；Docker 镜像内置；**RPM 包内嵌无需预装** |
| Docker | 20+ + Compose v2 | 仅 Docker Compose 方式需要 |
| 数据库 | SQLite（默认，零依赖）/ MySQL 8 / PostgreSQL 12+ | 三选一，由 `COMPOSE_PROFILES` 切换 |
| Redis | 7.x | 会话与瞬时状态 |
| 浏览器 | Chrome / Edge / Firefox | 支持 WebRTC |

### 2.2 服务与端口规划

| 服务 | 默认端口 | 协议 | 环境变量 |
|------|---------|------|---------|
| 前端 Web | 8081（开发）/ 80（Docker） | HTTP | `FRONT_PORT` |
| API | 8080 | HTTP | `API_PORT` |
| 信令 | 8082 | WebSocket | `WS_PORT` |
| mediasoup RTC | 40000-41000 | UDP | `RTC_MIN_PORT` / `RTC_MAX_PORT` |
| 离线网关 | 8088 | HTTP | `GATEWAY_PORT` |
| Caddy（生产） | 80, 443 | HTTP/HTTPS | — |

### 2.3 防火墙与安全组

> ⚠️ **部署前必读：端口连通性校验**
>
> WebRTC 音视频媒体走 **UDP 40000-41000**，与 Web/API 的 TCP 端口是两套独立通路。云平台通常默认只放行 80/443，**必须单独放行 UDP 40000-41000 入方向**，否则会议能进入但看不到对方、听不到声音。

| 需放行端口 | 协议 | 用途 | 备注 |
|-----------|------|------|------|
| 80 / 443 | TCP | Web 访问 | Caddy 生产入口 |
| 8088 | TCP | 离线网关 | 仅离线包方式 |
| 40000-41000 | UDP | WebRTC 媒体 | **云平台安全组必须单独放行** |

部署后在客户端验证端口连通性（PowerShell）：

```powershell
# TCP 443 应为 True（Web 信令）
Test-NetConnection -ComputerName <服务器IP> -Port 443 -InformationLevel Quiet
```

UDP 端口无法用 `Test-NetConnection` 直接测，可在服务器抓包确认：

```bash
tcpdump -i any -n 'udp and port 40055'   # 进会议后应有包到达
```

> 若服务器抓不到 UDP 包，说明云平台 NAT 层拦截，需联系云服务商开放。

## 三、Docker Compose 部署

适合有 Docker 环境的服务器。编排文件包含 MySQL/PostgreSQL、Redis、API、Realtime、Web、Caddy 全部服务。

> 📌 **要求**：Docker Compose v2.20+（支持 `include` 指令）。`docker-compose version` 查看版本。

默认入口为 `docker-compose.yml`，自动合并 `docker-compose.yml` 与 `docker-compose.override.yml`，数据库类型由 `.env` 里的 `COMPOSE_PROFILES` 控制（默认 SQLite，应用层 `DB_DRIVER` 自动跟随）。

### 3.1 在线构建部署

#### 步骤 1 — 准备环境文件

```bash
cp .env.production.example .env
vi .env
```

**必改项：**

| 变量 | 示例 | 说明 |
|------|------|------|
| `COMPOSE_PROFILES` | `sqlite`、`postgres` 或 `mysql` | 决定数据库类型，默认 `sqlite`（零依赖） |
| `SQLITE_PATH` | `/app/data/meeting.sqlite` | SQLite 文件路径（仅 `sqlite` 模式生效） |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `meeting` / `change-me` / `meeting` | PG 账号（用 PG 时） |
| `MYSQL_ROOT_PASSWORD` | `change-me-root` | MySQL root 密码（用 MySQL 时） |
| `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` | `meeting` / `change-me` / `meeting` | 业务库账号（用 MySQL 时） |
| `MEDIASOUP_ANNOUNCED_IP` | `10.0.0.10` | **客户端可达的公网/局域网 IP**，切勿用 127.0.0.1 |
| `MEDIASOUP_LISTEN_IP` | `0.0.0.0` | 监听地址 |
| `VITE_API_BASE` | `/api` | 前端调 API 的路径（经 Caddy 反代） |
| `VITE_WS_URL` | `auto` | WebSocket 地址，`auto` 表示同源 wss |

#### 步骤 2 — 生成证书（可选）

```bash
# 自签证书（内网测试）
bash deploy/docker/gen-selfsigned.sh <你的服务器IP或域名>
# 产物：deploy/docker/certs/fullchain.pem、privkey.pem

# CA 签发证书（信创环境推荐）
bash deploy/docker/gen-selfsigned.sh --ca <你的服务器IP>
# 产物：ca.crt（导入信任库）、fullchain.pem、privkey.pem
```

> 生产环境请替换为正式证书（放入 `deploy/docker/certs/`）。
> 信创环境使用 `--ca` 参数，并将 `ca.crt` 导入客户端浏览器/系统根信任机构。

#### 步骤 3 — 启动

```bash
# 构建并启动（首次启动自动跑迁移并写入管理员）
docker-compose up -d --build
```

> 💡 api 容器启动时会自动执行数据库迁移并写入默认管理员 `admin/admin123`（migrate 与 seed 均幂等，可重复执行）。

> 🔧 **mediasoup 构建说明（国内服务器/老内核）**
>
> mediasoup 的 C++ worker 需在构建时编译。国内网络下 GitHub releases 与 Meson WrapDB 常超时，Dockerfile 已内置以下处理：
> - 通过 `--ignore-scripts` 先装依赖，再用 `patch-mediasoup-wrap.cjs` 把 meson wrap 文件的下载 URL 重定向到 GitHub 代理（默认 `https://gh-proxy.com`）
> - pip 走清华源下载 meson/ninja/invoke
> - 如默认代理不可用，可换源构建：
>   ```bash
>   docker-compose build --build-arg GHPROXY=https://ghproxy.net --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple realtime
>   ```
> - mediasoup 3.22.0 未发布 kernel<6 的预编译包，CentOS 7 等老内核系统**必须**走本地编译，构建耗时约 10-15 分钟属正常现象

#### 步骤 4 — 访问验证

| 项 | 地址 |
|----|------|
| 浏览器入口 | `https://<服务器IP>/` |
| 默认账号 | `admin / admin123`（超级管理员）；另有三员账号见 [默认账号说明](#默认账号) |
| 健康检查 | `curl -k https://127.0.0.1/api/healthz` |

#### 步骤 5 — 停止与清理

```bash
# 停止服务（保留数据卷）
docker-compose down

# 彻底清理（含数据卷，谨慎）
docker-compose down -v
```

#### 步骤 6 — 重建单个服务

```bash
docker-compose up -d --build web      # 只重建前端
docker-compose up -d --build api      # 只重建 API
```

### 3.2 离线 Docker 镜像部署

适合目标机无外网的环境。在**同架构的构建机**上打包，拷贝到目标机加载后直接 `docker-compose up -d`。

#### 步骤 1 — 构建离线包（构建机，需联网与 Docker）

构建机要求：与目标机**相同 CPU 架构**，Node.js 20+（运行打包脚本），Docker 20+。

> 📌 `pack:docker` 脚本仅调用 `docker build` 打包镜像，不依赖本地 `node_modules`，无需 `npm install`。所有依赖安装在 Dockerfile 内通过 `npm ci` 完成。

```bash
npm run pack:docker
# 产物：dist/docker/ 目录
```

ARM64（如鲲鹏、飞腾）构建：

```bash
DOCKER_PLATFORM=linux/arm64 npm run pack:docker
```

> 💡 **npm 源不可达时的替代方案**：`package-lock.json` 中所有包的 `resolved` 地址已指向淘宝镜像（`registry.npmmirror.com`），Docker 内 `npm ci` 会直接使用。如构建机连淘宝源也不可达，可在项目根放 `.npmrc` 指向可达的内网私服，或改用 3.1 在线构建方式。

产物内容：

```
dist/docker/
├── meeting-app-<platform>-latest.tar      # 应用镜像（api/realtime/web）
├── meeting-base-<platform>-latest.tar     # 基础镜像（mysql/pg/redis/caddy）
├── docker-compose.yml                      # 编排文件
├── docker-compose.yml
├── docker-compose.yml
├── Caddyfile
├── .env.example
├── load-images.sh                          # 一键加载镜像
├── deploy/docker/gen-selfsigned.sh         # 证书生成脚本
└── README.txt
```

#### 步骤 2 — 目标机部署

```bash
# 拷贝整个 dist/docker/ 目录到目标机后
cd dist/docker

# 1) 加载全部镜像
bash load-images.sh

# 2) 配置环境
cp .env.example .env
vi .env                    # 改 MEDIASOUP_ANNOUNCED_IP、数据库密码等

# 3) 生成证书（可选）
# 自签证书（内网测试）
bash deploy/docker/gen-selfsigned.sh <服务器IP>
# 或 CA 签发证书（信创环境推荐）
bash deploy/docker/gen-selfsigned.sh --ca <服务器IP>

# 4) 启动（默认 SQLite + 自动初始化）
docker-compose up -d
```

> 离线包内的 compose 文件与源码完全一致，`docker-compose up -d` 命令无需任何额外参数。后续停止、重建、清理命令与 3.1 在线部署完全相同。

## 四、离线发布包部署

适合内网无外网环境。在**同架构的 Linux 构建机**上打包，拷贝 tar 包到目标机安装。目标机**无需访问 npm 网络**。

> 📌 适用于国产系统（银河麒麟 V10、统信 UOS、中科方德等），支持 x86_64 与 aarch64（鲲鹏、飞腾、海光）。

### 4.1 构建离线包（构建机，需联网）

构建机要求：与目标机**相同 CPU 架构**的 Linux（mediasoup 原生模块不可跨架构），Node.js 20+，可访问 npm。

```bash
cd /path/to/meeting
npm install
npm run pack:native
```

产物：

```
dist/native/
├── meeting-linux-arm64-YYYYMMDD.tar.gz   # 或 x64
└── README.txt
```

> ⚠️ 仅调试时可用 `PACK_NATIVE_FORCE=1 npm run pack:native` 强制在非 Linux 打包，但产出的 mediasoup 可能无法在目标 Linux 运行。

### 4.2 目标机准备

前置条件：

| 组件 | 要求 |
|------|------|
| Node.js | 20+（在 PATH 中） |
| Redis | 7.x |
| 数据库 | SQLite（默认，零依赖）/ MySQL 8 / PostgreSQL 12+ |

建库示例（MySQL）：

```sql
CREATE DATABASE IF NOT EXISTS meeting DEFAULT CHARACTER SET utf8mb4;
CREATE USER IF NOT EXISTS 'meeting'@'%' IDENTIFIED BY 'meetingpass';
GRANT ALL PRIVILEGES ON meeting.* TO 'meeting'@'%';
FLUSH PRIVILEGES;
```

建库示例（PostgreSQL）：

```sql
CREATE USER meeting WITH PASSWORD 'meetingpass';
CREATE DATABASE meeting OWNER meeting;
```

### 4.3 安装

```bash
# 解压
tar -xzf meeting-linux-arm64-YYYYMMDD.tar.gz
cd meeting-linux-arm64-YYYYMMDD

# root 执行安装
sudo ./install.sh
```

`install.sh` 会自动完成以下操作：

1. 校验架构（与 `ARCH.txt` 比对）与 Node 版本
2. 创建系统用户 `meeting`
3. 部署到 `/opt/meeting`（可用 `MEETING_PREFIX` 改）
4. 生成 `/opt/meeting/conf/.env`
5. 安装 systemd 单元：`meeting-api` / `meeting-realtime` / `meeting-gateway`
6. 执行 `migrate` + `seed`
7. `enable --now` 三个服务

常用安装环境变量：

| 变量 | 默认 | 说明 |
|------|------|------|
| `MEETING_PREFIX` | `/opt/meeting` | 安装目录 |
| `MEETING_USER` | `meeting` | 运行用户 |
| `MEETING_SKIP_SEED` | `0` | 设为 `1` 跳过写入 admin |

```bash
sudo MEETING_PREFIX=/data/meeting MEETING_SKIP_SEED=1 ./install.sh
```

### 4.4 修改配置

```bash
sudo vi /opt/meeting/conf/.env
```

必改项：

- `MEDIASOUP_ANNOUNCED_IP`：客户端能访问的服务器 IP（局域网勿填 127.0.0.1）
- 数据库 / Redis 账号密码
- `DB_DRIVER=mysql` 或 `postgres`

改完后重启：

```bash
sudo systemctl restart meeting-api meeting-realtime meeting-gateway
```

### 4.5 访问验证

| 项 | 地址 |
|----|------|
| 浏览器入口 | `http://<服务器IP>:8088/`（`GATEWAY_PORT`） |
| API 健康检查 | `curl http://127.0.0.1:8088/api/healthz` |
| 默认账号 | `admin / admin123`（超级管理员）；另有三员账号见 [默认账号说明](#默认账号) |

### 4.6 服务管理（systemd）

```bash
# 启动/停止/重启
sudo systemctl start|stop|restart meeting-api
sudo systemctl start|stop|restart meeting-realtime
sudo systemctl start|stop|restart meeting-gateway

# 查看状态
sudo systemctl status meeting-api meeting-realtime meeting-gateway

# 实时日志
sudo journalctl -u meeting-api -f
# 或日志文件
tail -f /opt/meeting/logs/*.log
```

无 systemd 时用脚本：

```bash
sudo -u meeting /opt/meeting/bin/start-all.sh
sudo /opt/meeting/bin/stop-all.sh
```

### 4.7 安装后目录结构

```
/opt/meeting/
├── conf/.env                          # 配置文件
├── app/
│   ├── front/                         # 静态资源
│   ├── serve/api|realtime|shared|db   # 后端服务
│   └── node_modules/
├── bin/
│   ├── gateway.mjs                    # 内置 HTTP 网关
│   ├── start-all.sh
│   └── stop-all.sh
└── logs/                              # 日志目录
```

### 4.8 国产系统（麒麟 / UOS / 中科方德）注意事项

| 注意事项 | 说明 |
|---------|------|
| **mediasoup 原生模块编译** | 麒麟/UOS/中科方德自带 gcc 工具链可编译，但离线包要求**同架构**构建机。aarch64 机器需在 aarch64 Linux 上打包 |
| **Node.js 来源** | 建议从 NodeSource 或官方 tarball 安装 20+，国产系统自带版本可能偏低 |
| **Docker 安装** | 麒麟/UOS 软件源可能有 docker.io，版本较旧，建议用官方静态二进制 `docker-20.10.x.tgz` |
| **证书** | 内网无 CA 时用自签证书（`gen-selfsigned.sh`），或导入企业内部 CA 签发证书 |

| **systemd 版本** | 服务单元已兼容 **systemd 219**（银河麒麟 V10 SP1）。日志由服务内重定向写入 `/opt/meeting/logs/*.log`（标准输出与错误合并为同一文件），不使用 `StandardOutput=append:`（该语法需 systemd ≥ 240） |
| **SELinux** | 麒麟默认 `enforcing`，网关端口 8088 需放行：`semanage port -a -t http_port_t -p tcp 8088`；或临时 `setenforce 0` 验证是否为 SELinux 拦截 |
| **浏览器** | 客户端推荐奇安信浏览器（涉密版）/ UOS 浏览器 / Chrome 100+；前端构建目标为 ES2020，支持较老 Chromium 内核 |

## 五、RPM 包部署

适合中科方德、银河麒麟、CentOS 等 RPM 系国产操作系统。**内嵌 Node.js 运行时**，目标机无需预装 Node.js；**默认 SQLite + 内存 Redis**，零外部依赖；**不依赖任何 .sh 脚本**，所有管理操作通过 `node xxx.mjs` 或 `systemctl` 完成。

> 📌 **适用场景**：中科方德等安全策略禁止执行 `.sh` 脚本的国产 OS；需要企业级包管理（`rpm -ivh` / `rpm -Uvh` / `rpm -e`）的环境。

### 5.1 与离线发布包的区别

| 对比项 | 离线发布包（tar.gz + .sh） | RPM 包 |
|--------|--------------------------|--------|
| 安装方式 | `tar -xzf` + `./install.sh` | `rpm -ivh meeting-*.rpm` |
| Node.js | 需目标机预装 20+ | **RPM 内嵌**，目标机无需安装 |
| 数据库 | 需 MySQL/PG + Redis | **默认 SQLite + 内存 Redis**，零依赖 |
| 脚本依赖 | 依赖 `install.sh`、`start-all.sh` 等 `.sh` | **全部 `.mjs`**，通过 `node` 执行 |
| 服务注册 | `install.sh` 手动写 systemd 单元 | RPM 自动安装到 `/usr/lib/systemd/system/` |
| 数据库迁移 | `install.sh` 手动执行 migrate | **systemd `ExecStartPre` 自动迁移** |
| 升级 | 手动替换文件 | `rpm -Uvh` 自动升级 |
| 卸载 | 手动删文件 | `rpm -e meeting` 自动清理 |
| HTTPS | 需 Nginx | **gateway.mjs 自带 HTTPS** |
| 证书生成 | `gen-selfsigned.sh`（依赖 OpenSSL） | `gen-cert.mjs`（纯 JS，node-forge） |

### 5.2 构建 RPM 包（构建机，需 Docker）

构建机要求：安装 Docker，可联网（下载 Node.js 二进制 + npm 依赖）。

> 📌 `pack:rpm` 通过 Docker 容器编译原生模块（mediasoup、better-sqlite3），无需构建机预装编译工具链。

```bash

npm run pack:rpm
# 产物：dist/rpm/meeting-0.1-1.el7.x86_64.rpm
```

ARM64（鲲鹏、飞腾）构建：

```bash
TARGET_ARCH=arm64 npm run pack:rpm
# 产物：dist/rpm/meeting-0.1-1.el7.aarch64.rpm
```

自定义版本号：

```bash
RPM_VERSION=0.2 RPM_RELEASE=1 npm run pack:rpm
```

构建产物：

```
dist/rpm/
├── meeting-0.1-1.el7.x86_64.rpm    # RPM 安装包
└── README.txt                       # 安装说明
```

RPM 包内嵌内容：

```

├── runtime/bin/node                  # 内嵌 Node.js 20 二进制
├── app/
│   ├── serve/api/dist/               # API 编译产物
│   ├── serve/realtime/dist/          # 信令编译产物（含 mediasoup）
```

### 5.3 目标机安装

> ⚠️ 安装 RPM 不需要预装 Node.js、Redis、MySQL，RPM 内嵌 Node.js 且默认使用 SQLite + 内存 Redis。

```bash
# 安装 RPM 包
sudo rpm -ivh meeting-0.1-1.el7.x86_64.rpm
```

RPM 安装时自动完成：

1. 创建系统用户 `meeting`
2. 部署文件到 `/opt/meeting/`
3. 安装 systemd 单元到 `/usr/lib/systemd/system/`
4. 创建 `data/`、`logs/`、`certs/` 目录
5. 设置目录属主为 `meeting` 用户
6. 执行 `systemctl daemon-reload`

### 5.4 配置

**方式一：交互式配置（推荐）**

```bash
sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/configure.mjs
```

交互式引导完成：数据库选择 → Redis 配置 → WebRTC IP → 端口 → 证书生成 → 数据库迁移 → 种子管理员 → 启动服务。

**方式二：手动配置**

```bash
# 复制配置模板
sudo cp /opt/meeting/conf/env.example /opt/meeting/conf/.env

# 编辑配置
sudo vi /opt/meeting/conf/.env
```

**必改项：**

| 变量 | 示例 | 说明 |
|------|------|------|
| `MEDIASOUP_ANNOUNCED_IP` | `10.0.0.10` | **客户端可达的服务器 IP**，切勿用 127.0.0.1 |
| `DB_DRIVER` | `sqlite` | 数据库类型：`sqlite`（默认）/ `mysql` / `postgres` |
| `REDIS_HOST` | `memory` | Redis：`memory`（默认，单节点零依赖）/ `127.0.0.1` |

**数据库切换（可选）：**

默认 SQLite 零依赖。如需切换 MySQL 或 PostgreSQL，编辑 `.env`：

```bash
# MySQL
DB_DRIVER=mysql
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=meeting
MYSQL_PASSWORD=meetingpass
MYSQL_DATABASE=meeting

# PostgreSQL
DB_DRIVER=postgres
PGHOST=127.0.0.1
PGPORT=5432
PGUSER=meeting
PGPASSWORD=meetingpass
PGDATABASE=meeting
```

建库 SQL 参见 [4.2 目标机准备](#42-目标机准备)。

**生成证书（可选，纯 JS 不依赖 OpenSSL）：**

```bash
# 自签证书（内网测试）
sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/gen-cert.mjs <服务器IP>
# 产物：/opt/meeting/certs/fullchain.pem、privkey.pem

# CA 签发证书（信创环境推荐）
sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/gen-cert.mjs --ca <服务器IP>
# 产物：/opt/meeting/certs/ca.crt（导入信任库）、fullchain.pem、privkey.pem
```

> 生成证书后 gateway.mjs 自动启用 HTTPS。未生成证书时 gateway 以 HTTP 模式运行。
> 信创环境使用 `--ca` 参数生成 CA 签发证书，并将 `ca.crt` 导入客户端浏览器/系统根信任机构。

### 5.5 启动服务

```bash
# 刷新 systemd
sudo systemctl daemon-reload

# 启用并启动
sudo systemctl enable --now meeting-api meeting-realtime meeting-gateway
```

> 💡 `meeting-api.service` 配置了 `ExecStartPre` 和 `ExecStartPost`，服务启动前会**自动执行数据库迁移**和**种子管理员**，无需手动操作。

|----|------|

| 默认账号 | `admin / admin123`（超级管理员）；另有三员账号见 [默认账号说明](#默认账号) |

> ⚠️ 登录后请立即修改默认密码。

### 5.7 服务管理

```bash

sudo systemctl start|stop|restart meeting-api
```

## 七、HTTPS 配置

> ⚠️ 生产环境必须启用 HTTPS（WebRTC 在非 localhost 下要求安全上下文）。

### 7.0 证书模式选择

| 模式 | 适用场景 | 命令 | 说明 |
|------|---------|------|------|
| **自签证书** | 内网测试、非信创环境 | 见 7.1/7.2/7.3 | 浏览器手动信任，适合快速验证 |
| **CA 签发证书** | 信创涉密环境、生产环境 | `--ca` 参数 | 先生成根 CA → 导入信任库 → 签发服务器证书 |
| **正式证书** | 有企业 CA 的环境 | 放入 `fullchain.pem` + `privkey.pem` | 直接使用企业 CA 签发的证书 |

> 🔒 **信创涉密客户端特殊说明**：涉密环境的浏览器安全策略不允许直接信任"自签名证书"（即证书同时充当 CA 和服务器证书）。需要**两步操作**：
> 1. 先生成根 CA 证书，导入到客户端浏览器/系统根信任机构
> 2. 再由根 CA 签发带 IP SAN 的服务器证书，部署到服务器
>
> 使用 `--ca` 参数生成此类证书，详见各部署方式的说明。

### 7.1 Docker Compose + Caddy（默认）

`docker-compose.yml` 默认用 Caddy 终结 TLS，使用文件证书（`deploy/docker/certs/fullchain.pem` + `privkey.pem`）。

**自签证书（内网测试）：**

```bash
bash deploy/docker/gen-selfsigned.sh <服务器IP或域名>
```

**CA 签发证书（信创环境推荐）：**

```bash
# 生成根 CA + 服务器证书（输出 ca.crt / fullchain.pem / privkey.pem）
bash deploy/docker/gen-selfsigned.sh --ca <服务器IP>
# → ca.crt 导入客户端浏览器信任库
# → fullchain.pem + privkey.pem 部署到 deploy/docker/certs/
```

**正式证书：** 将企业 CA 签发的 `fullchain.pem` 和 `privkey.pem` 放入 `deploy/docker/certs/`。

**域名访问：** 参考 `deploy/docker/Caddyfile.https.example`，替换 `meeting.example.com` 为你的域名。

### 7.2 离线包 + Nginx（推荐）

内置网关仅 HTTP。生产 HTTPS 推荐用 Nginx 终结 TLS：

```bash
# 离线包内置 genssl.sh，生成 CA 根证书 + 服务器 IP 证书
# 默认输出到 /opt/meeting/certs，无需手动创建目录
sudo /opt/meeting/bin/genssl.sh <服务器IP>
# 示例：sudo /opt/meeting/bin/genssl.sh 192.168.1.100
# → ca.crt 导入客户端信任库，fullchain.pem + privkey.pem 已在 /opt/meeting/certs/

# 使用 Nginx 终结 TLS
sudo systemctl disable --now meeting-gateway
sudo cp /opt/meeting/conf/nginx-meeting-ssl.conf /etc/nginx/conf.d/meeting-ssl.conf
# 编辑 server_name 与证书路径
sudo nginx -t && sudo systemctl reload nginx

# 或使用 gateway 内置 HTTPS
# 编辑 /opt/meeting/conf/.env 设置 GATEWAY_TLS_CERT 和 GATEWAY_TLS_KEY
sudo systemctl restart meeting-gateway
```

> `genssl.sh` 已内置在离线包 `bin/` 目录中，安装后位于 `/opt/meeting/bin/genssl.sh`，依赖系统自带的 OpenSSL。

### 7.3 RPM 包 + Gateway 内置 HTTPS（推荐）

RPM 部署的 `gateway.mjs` 自带 HTTPS 支持，无需 Nginx。网关启动时自动检测 `certs/` 目录：

```bash
# 生成自签证书（纯 JS，不依赖 OpenSSL）
sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/gen-cert.mjs <服务器IP>
# 产物：/opt/meeting/certs/fullchain.pem、privkey.pem

# 生成 CA 签发证书（信创环境推荐）
sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/gen-cert.mjs --ca <服务器IP>
# 产物：/opt/meeting/certs/ca.crt（导入信任库）、fullchain.pem、privkey.pem

# 重启网关即可生效
sudo systemctl restart meeting-gateway
```

> 证书存在时 gateway 自动以 HTTPS 模式运行；证书不存在时以 HTTP 模式运行。无需修改任何配置。

**使用正式证书：**

将企业 CA 签发的 `fullchain.pem` 和 `privkey.pem` 放入 `/opt/meeting/certs/` 目录，重启 `meeting-gateway` 即可。

### 7.4 HTTPS 校验要点

- 证书域名/IP 与浏览器访问地址一致
- WebSocket 走 `wss://`，前端 `VITE_WS_URL=auto` 会自动同源
- mediasoup 的 `MEDIASOUP_ANNOUNCED_IP` 与证书 SAN 匹配
- 防火墙放行 443
- **信创涉密环境**：必须使用 `--ca` 模式生成证书，并将 `ca.crt` 导入客户端浏览器/系统根信任机构。自签证书（无 CA 链）在涉密浏览器中会被拒绝，不弹出信任选项。导入根 CA 后，所有由该 CA 签发的服务器证书自动被信任，无需逐个手动信任。

## 八、品牌定制（项目名与 Logo）

系统支持通过环境变量自定义**项目名称**和**浏览器标签图标（Logo）**，无需改代码。

### 8.1 环境变量

| 变量 | 作用 | 默认值 | 说明 |
|------|------|--------|------|
| `VITE_APP_NAME` | 项目名称 | `Meeting` | 浏览器标签标题、PWA 应用名 |
| `VITE_APP_LOGO` | Logo 图标路径 | `/favicon.svg` | 浏览器 favicon、PWA 图标之一 |

> ⚠️ 这两个变量在**前端构建时**注入，**修改后必须重新构建前端**（Docker 重建 web 镜像，离线包重新打包），运行时改 `.env` 不会生效。

### 8.2 替换 Logo 文件

默认 Logo 文件位于 `front/public/favicon.svg`（SVG）和 `front/public/icons/icon-192.png`、`icon-512.png`（PWA 图标）。

**方式一：替换同名文件（最简单）**

将自己准备的 logo 文件覆盖以下文件（保持文件名与格式不变）：

```
front/public/favicon.svg        # SVG 矢量 logo（推荐，自适应缩放）
front/public/icons/icon-192.png  # 192×192 PNG（PWA 必需）
front/public/icons/icon-512.png  # 512×512 PNG（PWA 必需）
```

然后重新构建前端，无需改 `.env`。

**方式二：使用自定义文件名（通过环境变量指定）**

1. 将自己的 logo 放入 `front/public/`，例如 `front/public/mylogo.svg`
2. 在 `.env` 中设置：

   ```bash
   VITE_APP_LOGO=/mylogo.svg
   VITE_APP_NAME=我的会议系统
   ```

3. 重新构建前端

> 💡 `VITE_APP_LOGO` 指向的路径是前端静态资源根路径（`front/public/` 下），以 `/` 开头。SVG 优先（矢量清晰、体积小）；如用 PNG，建议同时提供 192 和 512 两个尺寸的图标文件以保证 PWA 显示效果。

**离线发布包：**

## 九、数据库切换

通过 `COMPOSE_PROFILES` 环境变量在 SQLite、MySQL、PostgreSQL 间切换，无需改代码（应用层 `DB_DRIVER` 自动跟随 `COMPOSE_PROFILES`）。

| 场景 | `COMPOSE_PROFILES` | 其他变量 | 独立容器 | 适用场景 |
|------|------------|---------|---------|---------|
| **SQLite（默认）** | `sqlite` | `SQLITE_PATH`（可选） | 无 | 单机部署、零依赖、快速试用、小规模（<50 人并发） |
| MySQL | `mysql` | `MYSQL_HOST/PORT/USER/PASSWORD/DATABASE` | mysql 容器 | 中大规模、需独立数据库服务 |
| PostgreSQL | `postgres` | `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` | postgres 容器 | 中大规模、需高级特性、多实例横向扩展 |

### Docker Compose 切换

在 `.env` 里改 `COMPOSE_PROFILES` 后 `docker-compose up -d --build`：

```bash
# SQLite（默认，零依赖，数据存于 meeting-data volume）
COMPOSE_PROFILES=sqlite

# MySQL
COMPOSE_PROFILES=mysql

# PostgreSQL
COMPOSE_PROFILES=postgres
```

### 离线包切换

编辑 `/opt/meeting/conf/.env` 修改 `COMPOSE_PROFILES` 与对应连接参数，重启服务。

### RPM 包切换

编辑 `/opt/meeting/conf/.env` 修改 `DB_DRIVER` 与对应连接参数，重启服务：

```bash
# 编辑配置
sudo vi /opt/meeting/conf/.env
#   DB_DRIVER=sqlite  （默认，零依赖）
#   DB_DRIVER=mysql   （需预装 MySQL）
#   DB_DRIVER=postgres（需预装 PostgreSQL）

# 重启服务（API 启动时自动迁移）
sudo systemctl restart meeting-api meeting-realtime meeting-gateway
```

> 💡 RPM 默认 `DB_DRIVER=sqlite` + `REDIS_HOST=memory`，完全零外部依赖。切换到 MySQL/PG 后需确保数据库可达。

### SQLite 数据备份与迁移

数据文件位于 Docker volume `meeting-data` 的 `/app/data/meeting.sqlite`，备份只需拷贝该单文件：

```bash
docker-compose cp api:/app/data/meeting.sqlite ./meeting-backup.sqlite
```

### SQLite 局限

- 单写者模型，写并发串行（WAL 模式下读并发无锁），百人级以上建议切 PG
- 不支持 realtime 多实例横向扩展（文件锁限制），单机部署无此问题

> 💡 迁移脚本按方言分目录：`serve/api/src/sql/{sqlite,mysql,postgres}/`，`migrate` 命令会自动选用。

## 十、会议录制

系统内置会议录制功能，采用客户端 Canvas 合成 + 服务端存储方案。

### 10.1 工作原理

1. 参会者点击控制栏「录制」按钮开始录制
2. 浏览器在本地用 Canvas 将所有视频画面合成宫格布局，混合所有音频轨道，通过 `MediaRecorder` 编码为 WebM
3. 停止录制后文件自动上传到服务端 API 存储，可在「录制」历史页查看、下载、删除
4. 录制期间会议头部显示红色录制指示器（含时长）

### 10.2 权限控制

| 角色 | 默认 | 主持人开启「开启录制」后 |
|------|------|------------------------|
| 主持人 | 始终可录制 | 始终可录制 |
| 参会者 | 不可录制 | 可录制 |

- 「开启录制」开关位于会议内「设置」面板，仅主持人可见，默认不勾选
- 任意参会者开始/停止录制时，主持人和其他参会者会收到 Toast 提示

### 10.3 存储与配置

录制文件默认存储于 `meeting-data` Docker 卷下的 `/app/data/recordings/` 目录，通过环境变量 `RECORDINGS_DIR` 可自定义：

```bash
# .env
RECORDINGS_DIR=/app/data/recordings
```

| 部署方式 | 录制目录 |
|---------|---------|
| Docker Compose | 随 `meeting-data` 卷持久化，无需额外配置 |
| 离线包 | `/opt/meeting/data/recordings/`，随安装目录持久化 |
| RPM 包 | `/opt/meeting/data/recordings/`，随安装目录持久化 |

- 录制文件以 WebM 格式存储，单文件上限 1GB（上传限制）
- 删除录制时同时删除物理文件

### 10.4 录制历史

侧边栏「录制」入口进入录制历史页，可查看本人所有录制（标题、所属会议、时长、大小、创建时间），支持下载与删除。仅能查看本人创建的录制。

### 10.5 限制说明

- 录制画面为 1280×720、15fps、1.5Mbps，适合常规会议回看，非高清直播级
- 录制内容为合成画面（宫格布局），非独立轨道；如需单独画面需后续扩展
- 浏览器需支持 `MediaRecorder` 与 `canvas.captureStream`（Chrome/Edge/Firefox 均支持）

## 十二、故障排查

### 12.1 常见问题速查

| 现象 | 可能原因 | 处理 |
|------|---------|------|
| 浏览器无法打开 | 网关/Caddy 未起或防火墙 | `systemctl status meeting-gateway` / `docker-compose ps`；放行 80/443/8088 |
| 能开页面但无法登录 | API 未起或数据库连不上 | `curl http://127.0.0.1:8080/healthz`；查 `.env` 数据库配置 |
| 登录后进会议黑屏/无声 | WebRTC 不通 | 见下方「WebRTC 媒体不通诊断」 |
| 能进会议，本地画面正常但看不到/听不到对方 | UDP 媒体端口被拦截 | **云平台安全组未放行 UDP 40000-41000**；或服务器防火墙拦截 |
| 看不到别人视频 | 远端摄像头关或信令未通 | 确认对方开了摄像头；查浏览器控制台 WS 是否连上；realtime 日志 |
| 共享全屏时画面无限嵌套 | 已自动处理 | 共享者本地不渲染自己的共享预览（网格中无该画面），控制栏/沉浸条显示共享状态，属正常 |
| 共享时看不到参会者 | 未开启沉浸模式 | 点会议头部「沉浸模式」，小窗显示参会者摄像头（可拖动到非共享屏幕避免被共享） |
| mediasoup realtime 起不来 | 架构不匹配 | 离线包需同架构构建；查 `ARCH.txt`；`journalctl -u meeting-realtime` |
| `pipefail: invalid option name` | Shell 脚本 CRLF 行尾 | `dos2unix` 脚本；仓库已加 `.gitattributes` 强制 LF |
| DB 连接 3306/5432 拒绝 | 库未起或地址错 | 确认 `DB_DRIVER` 与对应连接参数；`netstat -tlnp \| grep 3306` |
| 仅 API 502 | api 进程崩溃 | `systemctl status meeting-api`；查 `/opt/meeting/logs/api.log`（标准输出与错误**已合并到同一 .log 文件**） |
| 证书不信任 | 自签证书 | 浏览器手动信任，或导入企业 CA 根证书 |
| `Permission denied` | 脚本无执行权限 | `chmod +x *.sh` |
| RPM 安装后服务未自动启动 | 需手动启动 | `sudo systemctl enable --now meeting-api meeting-realtime meeting-gateway` |
| RPM 方式 `node` 命令找不到 | 未使用内嵌 node | 使用完整路径 `/opt/meeting/runtime/bin/node` |
| RPM 方式 configure.mjs 报错 | 权限不足 | `sudo /opt/meeting/runtime/bin/node /opt/meeting/bin/configure.mjs` |
| 内存 Redis session 丢失 | 进程重启 | 单节点模式正常现象，重启后需重新登录；多节点需切换外部 Redis |

### 12.2 WebRTC 媒体不通诊断

> 🔧 **典型现象**：能进入会议、本地画面正常、聊天能用，但看不到对方视频、听不到对方声音。这是云部署最常见问题，根因几乎都是 **UDP 媒体端口被拦截**，与代码无关。

排查步骤（按顺序）：

**1. 确认 `MEDIASOUP_ANNOUNCED_IP`**

应为客户端可达的公网 IP，不能是 127.0.0.1 或内网 IP。

```bash
docker-compose exec realtime printenv MEDIASOUP_ANNOUNCED_IP
```

**2. 确认服务器本地防火墙放行 UDP**

```bash
# firewalld
firewall-cmd --list-ports          # 应包含 40000-41000/udp
# 或 iptables
iptables -L -n | grep -i udp
```

**3. 抓包确认 UDP 是否到达服务器（关键一步）**

```bash
# 在服务器执行，然后客户端进会议
tcpdump -i any -n 'udp and port 40055'
```

- **抓不到任何包** → UDP 流量根本没到服务器，是云平台 NAT 层拦截，联系云服务商在**安全组**放行 UDP 40000-41000 入方向
- **能抓到包**但客户端仍无画面 → 检查返回方向，可能是 NAT hairpinning 或客户端网络问题

**4. 云平台安全组配置（重点）**

- 阿里云、腾讯云、华为云等均需在**安全组规则**中单独添加 UDP 入方向规则
- 部分平台默认仅放行 80/443 TCP，**不会自动放行 UDP 高端口**
- 规则：协议 UDP，端口范围 40000-41000，源地址 0.0.0.0/0，入方向允许

**5. 客户端网络验证（PowerShell）**

```powershell
# TCP 443 应为 True（信令正常）
Test-NetConnection -ComputerName <服务器IP> -Port 443 -InformationLevel Quiet
```

信令通但媒体不通，即可确认是 UDP 端口问题。

**6. 兜底方案**

若云平台坚决不放行 UDP 高端口，可考虑部署 TURN over TCP 443 中继（需架构调整，目前未内置）。
