## 4. 部署路径（按确认优先级重排）

### 4.1 第一优先：Docker 镜像（x86_64 / aarch64）

容器内自带 glibc/OpenSSL/依赖，与宿主机（SP1 glibc 2.17）完全解耦，**SP1 上可直接运行**，无需任何二进制适配。

**交付物**：`meeting-api / meeting-realtime / meeting-web` 镜像 tar（`docker load` 离线导入）+ 部署 compose。

**SP1 适配要点**：
- **Compose 兼容**：现有 `docker-compose.prod.yml` 需要 Compose v2.20+。两个方案：
  - a) 离线包内附带 `docker-compose` v2 独立二进制（约 60MB，arm64/x64 各一）与安装脚本（推荐）；
  - b) 生成单文件 legacy compose（合并 include、去掉 `depends_on.required`），兼容 compose v1/老版本。
- **镜像内 worker**：realtime 镜像构建时已按平台使用预编译 worker（arm64 分支已实现）。
- **数据与端口**：宿主机挂载 `/opt/meeting/data|logs|certs`；防火墙放行 8088 / UDP 40000-40100。

### 4.2 第二优先：RPM / DEB（主机部署，目标机本地离线构建）

容器不可用时走主机安装。SP1 基线下**交叉构建不可行**（arm64 无 glibc-217 Node、loongarch 无预编译），采用 **A′ 目标机本地离线构建**：

**离线构建包（Offline Build Bundle）**：

| 组成 | 内容 |
|---|---|
| 源码 | 仓库源码（不含 node_modules） |
| Node 运行时 | x86_64 → glibc-217；aarch64 → musl（或系统 nodejs）；loongarch64 → loong64 |
| npm 离线依赖 | npm cache / node_modules tarball（`npm ci --offline`） |
| Python 离线包 | **meson / ninja / invoke wheel**（worker 编译必需；SP1 自带 python2 需预置 python3+venv 说明） |
| 编译工具链说明 | worker 需 **GCC ≥ 8**（SP1 自带 4.8.5/7.3 不达标 → 预置 devtoolset-11 / clang 离线包） |
| `build-local.sh` | 探测 OS/架构/glibc/systemd → 选运行时 → 离线装依赖 → 编译 worker 与 better-sqlite3 → 构建前端 → fpm 产出 RPM/DEB → 按 systemd 版本安装 unit |

**systemd 219 兼容（必改，见 §5.1）**。

### 4.3 第三优先：loongarch64（龙芯）

- 前置条件：**POC 验证**（1~2 人日）——在龙芯机器上验证 `linux-loong64` Node 运行 + mediasoup worker 本地编译 + better-sqlite3 编译通过。
- Node 运行时 ✅（loong64 已实测可用）；worker/原生模块**必须本地编译**（无预编译、无官方镜像）。
- Docker 形态暂不提供（无官方基镜像；后续可基于 Loongnix 自建，另行评估）。
- 不阻塞 x86_64 / aarch64 主路径。

## 6. 屏幕共享：无限嵌套 Bug 根因与解决方案

### 6.1 现象

共享**全屏（monitor）**时出现"画面套画面"的无限嵌套（droste 效应）；共享窗口/标签页时可能正常。

### 6.2 根因（代码级）

嵌套防护依赖 `front/src/components/VideoGrid.tsx:545-550` 的本地自捕获检测：

```ts
const localScreenIsSelf = (() => {
  if (!localScreenStream) return false;
  const track = localScreenStream.getVideoTracks()[0];
  const surface = track?.getSettings?.().displaySurface;
  return surface === "monitor" || surface === "window" || surface === "browser";
})();
```

**链路**：共享全屏 → 共享流包含本地会议 UI（含共享预览 tile）→ 预览 tile 再渲染共享流 → 无限递归。

防护机制为：`localScreenIsSelf === true` 时，预览 tile 用"正在共享自己的屏幕"占位符替换视频帧，切断递归。

**失效条件**：`MediaTrackSettings.displaySurface` 是较新的 Chromium 能力，**老内核浏览器（含奇安信涉密版可能基于的 Chromium 86~102）`getSettings()` 不返回该字段** → `surface === undefined` → 表达式恒为 `false` → 占位符不生效 → 嵌套。

> 附注：该检测失效同时影响三条链路——① 共享者本地预览；② 共享者真实屏幕上的会议窗口（远端看到共享流里嵌套）；③ 本地 canvas 录制合成（录制源含屏幕 track）。三者同源，修复检测即可全部切断。

### 6.3 解决方案（分层，推荐 L1 + L2）

**L1（必做，一行级修复）：`displaySurface` 缺失时保守视为自捕获**

```ts
const localScreenIsSelf = (() => {
  if (!localScreenStream) return false;
  const track = localScreenStream.getVideoTracks()[0];
  const surface = track?.getSettings?.().displaySurface;
  // 老内核/信创浏览器不返回 displaySurface —— 保守视为自捕获，杜绝嵌套
  if (surface == null) return true;
  return surface === "monitor" || surface === "window" || surface === "browser";
})();
```

- 效果：任何检测不到共享面类型的浏览器，本地预览一律显示占位符 → 嵌套链被切断（本地预览、屏幕上的会议窗口、录制合成三条链路同时生效）。
- 代价：此类浏览器上共享**窗口/标签页**时本地预览也显示占位符（看不到本地预览内容）。共享者仍可从任务栏确认共享状态，tile 标签注明"屏幕共享：张三"。业界会议软件普遍如此处理，可接受。

**L2（建议做）：占位符文案区分 + 共享状态提示**

占位符文案区分场景（"正在共享屏幕，本地预览已隐藏"），共享控制栏显示共享时长与"停止共享"入口，降低 L1 的体验损失。

**L3（可选增强，实测后决定）**：更精确的共享面探测

- `track.getCapabilities().displaySurface` 返回**可共享类型集合**：若仅含 `"monitor"` 可判定全屏共享；含 `"window"` 则无法判定当前选择 → 对仅 monitor 能力的情况精确替换，其余保守替换。仅在实测确认 L1 体验损失过大时再引入。

**L4（不采用）**：Web 层无法最小化/隐藏共享者自身浏览器窗口（安全限制），"共享时自动收起窗口"不可行，无需尝试。

### 6.4 奇安信涉密版屏幕共享实测清单

| 检查项 | 方法 | 判定 |
|---|---|---|
| `navigator.mediaDevices.getDisplayMedia` 存在性 | 控制台检测 | 缺失则屏幕共享功能整体不可用（涉密策略可能禁用）——需与浏览器厂商确认解禁方式 |
| 共享全屏 → 本地预览 | 修复后应显示占位符 | 验证 L1 生效 |
| 共享窗口 → 远端画面 | 远端正常显示，无嵌套 | 验证远端链路 |
| 共享时录制 | 回放无嵌套 | 验证录制链路 |
| VP8/H264 收发 | 与其他参会者互通 | 决定是否必须启用 H264 |
| 自动播放/说话检测/设备切换 | 入会即验证 | 已有兜底，复核 |
