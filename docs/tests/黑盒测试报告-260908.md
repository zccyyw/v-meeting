## 三、发现并修复的缺陷

| # | 严重度 | 缺陷 | 根因 | 修复 |
|---|--------|------|------|------|
| 1 | **P0** | **SQLite 部署下创建会议全挂**（快速/预约/申请发起/群组开会均 500） | 5 处路由直接绑定 `Date` 对象；better-sqlite3 不接受 Date（mysql2/pg 接受），**开发用 MySQL 掩盖了生产默认 SQLite 的致命 bug** | `serve/db/src/sqlite.ts` 驱动层统一归一化为 ISO-8601（带时区，保证 auth-bridge `new Date()` 精确解析），防再犯 |
| 2 | **P0** | 群组一键开会 500（SQL 语法错误） | `insertIgnorePrefix` 返回值已含 `INTO`，调用处又拼了一次 `INTO` | `meeting-groups.ts` 去掉重复 `INTO` |
| 3 | P1 | 同一申请可重复发起（每次新建一个会议） | `start` 无幂等保护 | 已发起（`meeting_id != null`）返回 400 `already_started` |
| 4 | P2 | 内存会话存储无界增长 | `login_attempts:*`/`login_lock:*`/`session_force:*` 过期条目仅惰性删除；用户名喷洒场景每条 ~250B 只增不删 | `redis.ts` MemoryRedis 增加 60s 周期清扫（`unref()` 不阻退出） |
| 5 | P3 | `peerIdToRoom` Map 泄漏 | 死代码（从未被读取）；kick/deny/endMeeting 三条路径不清理，无界增长 | `signal.ts` 直接删除该 Map |
| 6 | P3 | 日志清理定时器未 `unref`；大批量 DELETE 后 WAL 瞬时膨胀 | 一致性/运维体验 | `index.ts` 定时器 `unref()` + 清理后 `PRAGMA wal_checkpoint(TRUNCATE)` |

## 四、稳定性审查结论（无需修复的观察项）

- **realtime**：连接断开/异常/会议结束清理路径完善且幂等（closePeerMedia + leavePeer + router.close + rooms.delete）；定时器仅 1 个进程级心跳且 shutdown 清理；mediasoup 单 worker、router 随会议生命周期创建销毁、无空闲 router 残留；录制为纯客户端实现，服务端零资源。整体设计规范。
- **api**：上传用 `pipeline`（失败自动销毁流）+ 三处 unlink 兜底；operlog 钩子无每请求资源、写入失败静默兜底；SQLite WAL 依赖默认 auto-checkpoint（单连接短查询，无长读事务）。
- 观察项（低风险，记录备查）：endMeeting 时 DB 更新失败仅打日志，极端情况下会议可被有效 token "复活"；录制中 peer 直接断线时其他端的"录制中"指示残留至会议结束；operlog onResponse 对 `/sys-*` 重复 loadSessionUser（性能小瑕疵）。
- **需求符合性修正**：`sys.log.storageThreshold` 仅为配置项，**无实现该检查的后台任务**（此前文档误记为已实现）——已列入待完善清单。

## 五、结论

修复后全量回归通过（33+8+4），服务端零错误。**两个 P0 均属"开发环境数据库方言掩盖生产缺陷"类型**——建议后续 CI 在 SQLite 方言下跑本套黑盒脚本作为发布门禁。
