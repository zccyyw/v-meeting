# 需求改造设计方案

> 基于需求文档 `docs/xuqiu/meet-需求-260819.txt`，结合项目现有架构分析。
> 已与用户确认关键疑问点（见文末「需求确认记录」）。

---

## 整体架构概览

现有项目分为三层：
- **前端** (`front/`)：React + Ant Design，会议界面 + 系统管理界面
- **API 后端** (`serve/api/`)：Fastify + SQLite/MySQL/PostgreSQL，REST API
- **信令服务** (`serve/realtime/`)：WebSocket + mediasoup，WebRTC 音视频

改造原则：**配置驱动、类型安全、最小侵入**。尽量通过 `sys_config` 表参数化行为，避免硬编码；同模块需求合并设计，减少跨文件碎片化改动。

## 模块 A：会议邀请与在线状态（需求 1 + 2 + 4）

### 需求合并分析

| 需求 | 内容 | 确认结果 |
|------|------|---------|
| 1 | 会议前小分屏显示被邀请人员入会情况（在线/离线） | 前端看被邀请人员入会情况 |
| 2 | 会议管理后端只看到所有参会者的在线状态 | 按参会者个体显示在线状态 |
| 4 | 一键群组，从系统用户/部门中选择成员，快速来人开会 | 从系统用户/部门中选择 |

三者共享「邀请名单」和「在线状态」概念，合并设计。

### A.1 数据库改造

#### 新增表：`meeting_invitations`（会议邀请名单）

```sql
CREATE TABLE IF NOT EXISTS meeting_invitations (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  meeting_id  INTEGER NOT NULL,           -- 关联 meetings.id
  user_id     INTEGER,                     -- 被邀请用户（sys_user.user_id），NULL=外部邀请
  dept_id     INTEGER,                     -- 被邀请部门（sys_dept.dept_id），按部门邀请时填
  display_name TEXT,                       -- 显示名（冗余，外部邀请时用）
  status      TEXT DEFAULT 'pending',      -- pending/accepted/rejected/attended
  invited_at  DATETIME,
  joined_at   DATETIME,
  FOREIGN KEY (meeting_id) REFERENCES meetings(id) ON DELETE CASCADE
);
CREATE INDEX idx_meeting_invitations_meeting ON meeting_invitations(meeting_id);
CREATE INDEX idx_meeting_invitations_user ON meeting_invitations(user_id);
```

#### 新增表：`meeting_groups`（常用分组）

```sql
CREATE TABLE IF NOT EXISTS meeting_groups (
  group_id    INTEGER PRIMARY KEY AUTOINCREMENT,
  group_name  TEXT NOT NULL,
  owner_id    INTEGER NOT NULL,            -- 创建者（sys_user.user_id）
  created_at  DATETIME,
  FOREIGN KEY (owner_id) REFERENCES sys_user(user_id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS meeting_group_members (
  group_id    INTEGER NOT NULL,
  user_id     INTEGER NOT NULL,
  dept_id     INTEGER,                     -- 可选：按部门加入
  PRIMARY KEY (group_id, user_id)
);
```

迁移文件：`serve/api/src/sql/{sqlite,mysql,postgres}/007_meeting_invitations.sql`

### A.3 在线状态实现

**方案**：信令服务 `MeetingRoom` 已维护 `peers Map`，在此基础上：

1. `signal.ts` 的 `join` 处理中，同步更新 `meeting_invitations.status = 'attended'`
2. `signal.ts` 的 `leave` 处理中，同步更新 `meeting_invitations.status` 回 `pending`（可选）
3. 新增 `GET /meetings/:id/invitations` 路由：查询邀请名单，结合信令服务内存状态返回在线/离线

**信令服务 ↔ API 通信**：复用现有 `auth-bridge.ts` 直接查库的模式。在线状态查询走 API → DB（meeting_invitations.status），不依赖信令服务内存，避免跨进程复杂度。

#### 后端实现

新增 `serve/api/src/routes/meeting-groups.ts`：

```typescript
// POST /meeting-groups — 创建群组
// 1. zod 校验 groupName + memberUserIds + memberDeptIds
// 2. INSERT meeting_groups (group_name, owner_id, created_at)
// 3. 批量 INSERT meeting_group_members（user_id 和 dept_id 两种来源）
// 4. 返回群组 + 成员列表

// GET /meeting-groups — 我的群组列表
// 查询 WHERE owner_id = ? 或成员包含当前用户
// 返回列表含 memberCount（子查询 COUNT）

// PATCH /meeting-groups/:id — 修改群组成员
// 支持增量操作（add/remove），避免全量替换导致并发覆盖

// DELETE /meeting-groups/:id — 删除群组
// 先删 meeting_group_members 再删 meeting_groups

// POST /meeting-groups/:id/quick-start — 一键群组开会
// 1. 查群组成员列表（含部门展开后的所有用户）
// 2. 调用会议创建逻辑（复用 meetings.ts 的 POST /meetings 核心逻辑）
// 3. 批量 INSERT meeting_invitations（一人一条）
// 4. 返回会议 ID + 会议码 + 邀请人数
```

**部门展开逻辑**：选择部门加入群组时，实际存储 `dept_id`；一键开会时展开为该部门下所有用户：

```typescript
async function expandGroupMembers(db: Db, groupId: number): Promise<{ userId: number; displayName: string }[]> {
  // 查直接选中的用户
  const [userRows] = await db.query(
    `SELECT m.user_id, u.nick_name
     FROM meeting_group_members m
     JOIN sys_user u ON m.user_id = u.user_id
     WHERE m.group_id = ? AND m.user_id IS NOT NULL`,
    [groupId]
  );
  // 查选中的部门，展开为部门下所有用户
  const [deptRows] = await db.query(
    `SELECT u.user_id, u.nick_name
     FROM meeting_group_members m
     JOIN sys_user u ON u.dept_id = m.dept_id
     WHERE m.group_id = ? AND m.dept_id IS NOT NULL
       AND u.del_flag = '0' AND u.status = '0'`,
    [groupId]
  );
  // 合并去重
  const map = new Map<number, string>();
  for (const r of [...userRows, ...deptRows]) map.set(Number(r.user_id), r.nick_name);
  return [...map].map(([userId, displayName]) => ({ userId, displayName }));
}
```

## 模块 D：三员权限与安全合规（需求 6）

### 需求合并分析

| 子需求 | 内容 |
|--------|------|
| 6.1 | 三员账号：系统管理员、授权管理员、审计管理员 |

### D.1 三员账号与角色设计

#### 角色定义（通过 sys_role 种子数据，非硬编码）

| role_key | role_name | 职责 | 权限范围 |
|----------|----------|------|---------|
| `admin` | 超级管理员 | 全部权限 | 所有 `system:*` 权限 |
| `sys_admin` | 系统管理员 | 系统设置管理，添加机构、用户 | `system:dept:*`, `system:user:list/add/edit`, `system:config:*` |
| `auth_admin` | 授权管理员 | 审核用户增删改操作，查看审计管理员登录日志 | `system:user:approve`, `system:operlog:list` (登录日志) |
| `audit_admin` | 审计管理员 | 除自己外所有账号的登录操作日志 | `system:operlog:list/query/export` (全量) |

#### 用户操作审批流程

新增表 `sys_user_approval`（用户增删改审批）：

```sql
CREATE TABLE IF NOT EXISTS sys_user_approval (
  approval_id   INTEGER PRIMARY KEY AUTOINCREMENT,
  request_type   TEXT NOT NULL,           -- create/update/delete/resetPwd
  target_user_id INTEGER,                 -- 操作目标用户
  requester_id   INTEGER NOT NULL,        -- 申请人（系统管理员）
```

### F.3 通用配置读取层

新增 `serve/api/src/config-cache.ts`：

```typescript
// 配置缓存层 — 避免每次请求都查库
const configCache = new Map<string, { value: string; expires: number }>();
const CACHE_TTL = 60_000; // 1 分钟

export async function getConfig(db: Db, key: string, defaultValue: string = ''): Promise<string> {
  const cached = configCache.get(key);
  if (cached && cached.expires > Date.now()) return cached.value;
  
  const [rows] = await db.query(
    `SELECT config_value FROM sys_config WHERE config_key = ? LIMIT 1`, [key]
  );
  const value = (rows as { config_value?: string }[])[0]?.config_value ?? defaultValue;
  configCache.set(key, { value, expires: Date.now() + CACHE_TTL });
  return value;
}
```

所有配置项统一通过此函数读取，避免硬编码。
